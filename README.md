# search-r1-reproduce

A small-scale reproduction of Search-R1 based on the `recipes/search_tool` recipe
from tinker-cookbook. It uses BM25 retrieval, Qwen3.5 and LoRA training through a
self-hosted SkyRL Tinker service.

[Chinese version](README_zh.md)

## Experiment record

[Browse the experiments](experiments/README.md) for configurations, scores, complete
evaluation transcripts, short-training metrics, monitoring data and provenance.

- [Local baseline analysis](experiments/2026-11-16-local-baselines/BASELINE_ANALYSIS.md):
  five model/prompt configurations, 631 development questions each, evaluated with oMLX.
- [A100 validation](experiments/2026-11-16-a100-validation/README.md): deployment,
  padding optimization, microbatch/concurrency comparisons, checkpoint loading and resume.
- Formal training and its final evaluation have not yet been recorded in this archive.

The historical runs predate the Unicode renderer correction. Their original
configurations and scores are preserved; they are not measurements of the current
renderer. The [raw-log attachment manifest](experiments/attachments/README.md)
describes a locally prepared archive that has not been uploaded to GitHub Releases.

## Repository layout

- `search_r1/` adapts tinker-cookbook's `recipes/search_tool` recipe.
  - `tools.py` implements the BM25 search tool and the F1+ reward, with the original reward available as an option.
  - `search_env.py` defines the fast and original prompts, loads data, and builds the search environment.
  - `renderers.py` preserves Unicode in Qwen3.5 tool arguments, matching the model's chat template.
  - `train.py` is the cloud training entry point.
  - `offline_eval.py` supports Tinker and local oMLX evaluation and writes each trajectory to disk.
  - `local_completer.py` adapts oMLX for local inference.
- `retrieval/` runs the BM25 server in a separate uv environment. This repository adds `--host` and `--port` to the upstream `retrieval_server.py`.
- `eval_sets/` holds the fixed development and test sets generated by `scripts/make_eval_sets.py`.
- `experiments/` holds archived results and analysis intended for GitHub.
- `scripts/` contains deployment, evaluation and analysis tools; see the [script guide](scripts/README.md).
- `tests/` contains reward, cloud-operation and W&B compatibility checks.
- `data/` and `runs/` contain local datasets and working outputs. Git ignores both directories.
- `local_docs/` remains local and ignored; it is not part of the public experiment record.

Training and base-model evaluation default to
`search_r1/qwen3_5_disable_thinking_unicode`. This renderer preserves non-ASCII
characters in list/dict tool arguments; it retains the cookbook's message rendering,
parsing and rollout behavior. Its name is saved in training/evaluation configuration
and training-client metadata. Checkpoint evaluation uses the recorded renderer when
available. The original `qwen3_5_disable_thinking` remains available for historical runs.

## Download the data

Run these commands from the repository root.

```bash
mkdir -p data
(
    cd data
    hf download PeterJinGo/nq_hotpotqa_train --repo-type dataset --local-dir nq_hotpotqa_train
    hf download PeterJinGo/wiki-18-bm25-index --repo-type dataset --local-dir bm25-index
    hf download PeterJinGo/wiki-18-corpus --repo-type dataset --local-dir corpus
    gunzip -k corpus/wiki-18.jsonl.gz
)
```

## Set up the environments

```bash
uv sync
(cd retrieval && uv sync)
cp .env.example .env             # First-time setup
```

Set `OMLX_API_KEY` in `.env` for local evaluation and `WANDB_API_KEY` for
training. The training entry point reads `.env` from the repository root.
Existing environment variables take precedence.

Training logs to Weights & Biases (W&B) by default under the
`search-r1-reproduce` project. The generated run name includes the model, batch
size, learning rate, and timestamp. Set `wandb_project=<project_name>` to use a
different project, or `wandb_project=None` to disable uploads and keep local logs.

On the cloud machine, run `uv sync --locked` using the project's
`pyproject.toml` and `uv.lock` to install the pinned dependencies, including
`wandb`. Set `WANDB_API_KEY` on that machine and let uv create its environment.

## Cloud training

Start the SkyRL Tinker service and the BM25 retrieval server before running
training. Deployment scripts expect the cloud layout documented in the
[script guide](scripts/README.md). The following values illustrate the CLI; they
do not fix the scale or GPU for a future formal run.

```bash
TINKER_API_KEY=tml-dummy TINKER_BASE_URL=http://127.0.0.1:8000 \
    uv run python -m search_r1.train batch_size=64 group_size=8 max_steps=100 \
    save_every=5 log_path=/workspace/runs/search-r1-train
```

The training entry point defaults to 512 questions per batch, as in the
cookbook, so the example explicitly sets `batch_size=64`. The direct training CLI
defaults to `save_every=25`; the example overrides it to five steps.

To evaluate a saved checkpoint on the fixed development set, run
`search_r1.offline_eval` separately with `backend=tinker`,
`tinker_state_url` set to the full training-state URL from `checkpoints.jsonl`,
and `eval_file=eval_sets/dev.jsonl`. Self-hosted SkyRL requires this full-state
loading path; a sampler URL in `tinker_checkpoint_url` is not a reliable substitute.
The training flag `eval_every` does not run this evaluation.

For segmented training with development evaluation, the driver is
`scripts/cloud/train_with_dev_eval.sh <run_name> [extra train.py arguments]`.
Its defaults are `TOTAL_STEPS=100`, `BATCH_SIZE=64`, `GROUP_SIZE=8`,
`EVAL_EVERY=25`, `SAVE_EVERY=5`, `EVAL_CONCURRENCY=32`, `PRUNE_STATES=1` and
`UPLOAD=1`. Set these explicitly for the chosen run. It reads the saved training
configuration for evaluation and uploads checkpoints to W&B. Base-model evaluation
is a separate operation. The archived A100 tests do not establish that the complete
segmented driver and real upload/recovery workflow have been validated.

## Run the retrieval server

```bash
./retrieval/start.sh             # Defaults to 127.0.0.1:8001
./retrieval/stop.sh
```

The first startup can take a few minutes while the server converts the corpus
to an Arrow cache under `~/.cache/huggingface/datasets`.

## Evaluate models

Start oMLX before running a local evaluation. The base-model evaluation
script reuses a running retrieval server or starts one and stops it on exit.

```bash
./scripts/run_base_eval.sh                       # All five base-model configurations
LIMIT=50 ./scripts/run_base_eval.sh q35-fast      # One configuration, first 50 questions per source
uv run python scripts/compare_runs.py runs/eval/base-*
uv run python scripts/diagnose_run.py runs/eval/base-q35-fast-n50
```

To inspect the archived local baselines without generating new samples:

```bash
uv run python scripts/compare_runs.py experiments/2026-11-16-local-baselines/evaluations/base-*
uv run python scripts/diagnose_run.py experiments/2026-11-16-local-baselines/evaluations/base-q35-fast-n100
```

To run an evaluation directly, start the retrieval server first.

```bash
uv run python -m search_r1.offline_eval backend=omlx omlx_model=Qwen3.5-4B-bf16 \
    eval_file=eval_sets/dev.jsonl limit_per_source=10 run_name=try
```

Each run writes `config.json`, `trajectories.jsonl`, and `summary.json` under
`runs/eval/<run_name>/`. Completed historical evaluations have been moved to
`experiments/`; the per-experiment manifests retain their original paths and hashes.
